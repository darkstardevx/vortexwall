Network priority

Dropped before it's even
connection-tracked.

This box's iptables is already the nf_tables kernel backend, so ufw's rules and VortexWall's rules both run through nftables — as two independent tables, evaluated by hook priority.

VortexWall's prerouting chain runs at priority -300 — the raw tier — ahead of ufw's filter-tier rules. A banned IP never reaches connection tracking at all.

01vortexwall — prerouting, raw tierpriority -300
▾ dropped here, never continues ▾
02ufw — filter tier, connection trackedpriority 0
03application (sshd, etc.)userspace
Self-cleaning

Auto-expiring bans,
no cleanup thread.

Bans live in nftables' own set timeouts — the kernel expires them, not VortexWall. No cleanup thread, no orphaned rules if the daemon crashes or is killed mid-run.

A sliding window tracks per-IP failures (threshold within window_secs), not a raw lifetime count — so a handful of failures years apart never adds up to a ban.

config.toml
config
threshold    = 5      # failures before a ban
window_secs  = 600    # sliding window
ban_secs     = 3600   # nftables auto-expires it
allowlist    = []

[[watch]]
service = "sshd"
Guardrails

Some things are never
bannable. Hardcoded.

Loopback and every private range (RFC1918 + link-local + IPv6 ULA) are hardcoded-unbannable, regardless of config. Can't be overridden. Can't accidentally lock out a LAN you're on.

--dry-run runs the full detection pipeline with zero nftables writes and zero root required — validate against real traffic with no risk before trusting it.

Reversible

One command,
fully gone.

Explicitly a learning project ahead of setting up fail2ban for real. --teardown removes the entire nftables table — every rule, every ban — immediately. No manual nftables cleanup, ever.

Roadmap so far:
